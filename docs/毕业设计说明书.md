## 摘要

本课题围绕农产品质量追溯场景，设计并实现了一套“管理端 Web + 消费者小程序 + Spring Boot 后端 + openGauss 数据库”的一体化系统。系统以“基地—批次—生产记录—质检报告—溯源码—召回—反馈”为主线，支持管理端业务闭环维护与小程序端扫码/输入查询。

系统后端采用 Spring Boot 3.5.x、MyBatis 注解 SQL、JWT 风格 Bearer Token 鉴权和统一异常返回；数据库采用 openGauss（PostgreSQL 协议兼容）；前端管理端采用 Vue 3 + Vite + Element Plus，小程序端采用微信小程序原生框架。系统已实现角色隔离（ADMIN/OPERATOR/USER），将管理接口与公开查询接口分级控制，并完成文件上传、二维码生成、召回提示、反馈提交、查询历史与近 7 天查询量可视化等功能。

关键词：openGauss；农产品溯源；微信小程序；Spring Boot；Vue 3；权限隔离

## Abstract

This project designs and implements an integrated agricultural traceability system based on openGauss, including a Web admin console, a WeChat mini-program client, backend services, and relational data persistence. The system models the full lifecycle of traceability data through farm bases, product batches, production records, inspection reports, trace codes, recalls, and user feedback.

The backend is implemented with Spring Boot and MyBatis, exposes RESTful APIs, and applies Bearer-token authentication with unified response handling. The Web admin uses Vue 3 and Element Plus, while the mini-program provides consumer-facing trace query interactions via input and QR scanning. The implementation includes role-based access isolation (ADMIN/OPERATOR/USER), trace-code generation and aggregation query, attachment upload, recall warning display, feedback workflow, and recent-query visualization.

KEY WORDS: openGauss; Agricultural Traceability; WeChat Mini Program; Spring Boot; Vue 3; RBAC

## 第1章 绪论

### 1.1 课题背景

农产品供应链链路长、环节多，传统记录方式普遍存在“数据分散、追责慢、查询成本高”的问题。质量异常发生后，企业与监管方需要快速定位基地、批次、生产行为、质检结论与召回状态。与此同时，消费者对“来源可信、过程可查、问题可追”的透明度要求持续提升。

### 1.2 研究意义

1. 对企业：建立标准化追溯档案，降低异常定位与召回沟通成本。  
2. 对消费者：通过小程序低门槛查询批次全链路信息。  
3. 对监管协同：形成可结构化查询的数据证据链。  
4. 对工程实践：形成国产数据库 + 前后端分离 + 小程序多端协同的完整实现案例。

### 1.3 设计目标

1. 构建管理端业务闭环：基地、批次、生产、质检、溯源码、召回、用户。  
2. 构建消费者查询闭环：输入/扫码查询、详情展示、历史、反馈。  
3. 落地角色权限隔离：ADMIN/OPERATOR/USER 不同数据访问边界。  
4. 形成可持续扩展的工程骨架：统一响应、统一异常、统一鉴权、模块化服务。

4. openGauss 提供核心关系数据存储。

## 第3章 需求分析

### 3.1 角色定义

1. `ADMIN`：系统管理员，具备全部管理权限（含用户/角色管理）。  
2. `OPERATOR`：业务操作人员，具备业务数据管理权限。  
3. `USER`：消费者/小程序用户，仅进行查询与反馈等前台功能。

### 3.2 功能需求

#### 3.2.1 管理端功能

1. 认证：登录、当前用户信息、个人信息修改。  
2. 基地管理：新增、编辑、删除、列表、分页。  
3. 批次管理：新增、编辑、删除、列表、分页。  
4. 生产记录管理：新增、编辑、删除、列表、分页。  
5. 质检报告管理：新增、编辑、删除、列表、分页。  
6. 溯源码管理：按批次查看、生成溯源码。  
7. 召回管理：发起召回、关闭召回、删除召回记录。  
8. 仪表盘统计：基地数、批次数、溯源码数、生产记录数、质检报告数、进行中召回数。  
9. 用户与角色管理（仅管理员）。

#### 3.2.2 小程序功能

1. 溯源查询：首页输入追溯码/扫码查询。  
2. 详情展示：基地、批次、生产、质检、召回。  
3. 报告预览：图片/PDF 预览页面。  
4. 查询历史：历史列表、清空、删除、近 7 天查询量可视化。  
5. 账号能力：微信登录、账号密码登录、注册、绑定。  
6. 反馈能力：提交反馈、查看我的反馈。

### 3.3 非功能需求

1. 安全性：基于 Token 的接口鉴权与角色权限控制。  
2. 一致性：统一 `ApiResponse` 返回结构。  
3. 可维护性：按 `controller/service/mapper/dto/vo/entity` 分层。  
4. 可扩展性：溯源码签名字段预留防伪扩展能力。

## 第4章 系统总体设计

### 4.1 模块划分

1. 认证与鉴权模块。  
2. 基础档案模块（基地、批次）。  
3. 过程记录模块（生产、质检）。  
4. 溯源码模块（生成、查询聚合）。  
5. 召回模块。  
6. 反馈模块。  
7. 统计模块。  
8. 文件服务模块。  
9. 用户与角色模块。

### 4.2 权限边界设计（按当前实现）

1. `ADMIN`：可访问全部管理接口。  
2. `OPERATOR`：可访问业务管理接口（基地/批次/生产/质检/溯源码/召回/仪表盘/上传）。  
3. `USER`：不可访问管理接口；可访问公开溯源查询与反馈相关接口。

### 4.3 关键数据流

1. 管理数据流：登录 → 创建基地/批次 → 录入生产与质检 → 生成溯源码 → 发起或关闭召回。  
2. 消费数据流：扫码/输入追溯码 → 调用公开查询接口 → 展示聚合结果 → 保存本地历史 → 可提交反馈。

## 第5章 数据库设计

### 5.1 核心表

1. `sys_user`：用户主表。  
2. `sys_role`：角色字典（ADMIN/OPERATOR/USER）。  
3. `sys_user_role`：用户角色关联表。  
4. `base_info`：基地信息。  
5. `product_batch`：产品批次。  
6. `production_record`：生产记录。  
7. `inspection_report`：质检报告。  
8. `trace_code`：溯源码。  
9. `recall_record`：召回记录。  
10. `user_feedback`：用户反馈。

### 5.2 关系设计

1. `base_info` 1:N `product_batch`。  
2. `product_batch` 1:N `production_record`。  
3. `product_batch` 1:N `inspection_report`。  
4. `product_batch` 1:N `trace_code`。  
5. `product_batch` 1:N `recall_record`。  
6. `sys_user` N:M `sys_role`（通过 `sys_user_role`）。

### 5.3 索引与约束

1. `username`、`batch_code`、`report_no`、`trace_id` 均有唯一约束。  
2. 高频查询字段（如 `batch_id`、`operation_time`、`created_at`）建立索引。  
3. 所有核心业务表均具备时间字段用于追踪。

### 5.4 数据表详细说明

#### 5.4.1 `sys_user`（系统用户表）

用途：存储管理端用户与小程序用户的统一账户信息。  

关键字段说明：

1. `id`：用户主键，自增。  
2. `username`：用户名，唯一约束。管理端账号登录依赖该字段。  
3. `password`：加密后的密码（后端使用 `PasswordUtil` 编码与校验）。  
4. `real_name`：真实姓名，用于页面展示与操作记录归属。  
5. `phone`：手机号，可为空。  
6. `openid`：微信登录标识，唯一索引，用于微信登录与账号绑定。  
7. `status`：账号状态，`1=启用`，`0=停用`。  
8. `created_at/updated_at`：创建与更新时间。  

业务规则：

1. `username` 不可重复。  
2. `openid` 不可重复，避免同一微信身份绑定多个账户。  
3. 账号停用后不能通过鉴权加载为当前用户。

#### 5.4.2 `sys_role`（角色表）

用途：定义角色字典。当前系统预置 `ADMIN`、`OPERATOR`、`USER`。  

关键字段说明：

1. `id`：角色主键。  
2. `role_code`：角色编码，唯一。权限判断主要依据该字段。  
3. `role_name`：角色名称。  
4. `remark`：角色说明。  
5. `created_at`：创建时间。  

#### 5.4.3 `sys_user_role`（用户角色关联表）

用途：建立用户与角色的多对多关系。  

关键字段说明：

1. `user_id`：用户ID。  
2. `role_id`：角色ID。  
3. 联合主键：`(user_id, role_id)`，防止重复绑定同一角色。  

#### 5.4.4 `base_info`（基地信息表）

用途：记录基地档案，是批次数据的上游基础实体。  

关键字段说明：

1. `base_code`：基地编码，唯一。  
2. `base_name`：基地名称。  
3. `manager_name`：负责人。  
4. `contact_phone`：联系方式。  
5. `province/city/district/address`：地址分层字段。  
6. `acreage`：面积。  
7. `status`：基地状态，`1=启用`，`0=停用`。  
8. `created_at/updated_at`：审计字段。  

#### 5.4.5 `product_batch`（产品批次表）

用途：承载产品批次主信息，连接生产、质检、溯源码与召回。  

关键字段说明：

1. `batch_code`：批次号，唯一。  
2. `base_id`：所属基地ID（逻辑关联 `base_info.id`）。  
3. `product_name/product_category`：产品名称与类别。  
4. `planting_date/expected_harvest_date/actual_harvest_date`：关键时间节点。  
5. `quantity/unit`：产量与计量单位。  
6. `batch_status`：批次状态，前端约定 `0=待生产, 1=生产中, 2=已完成`。  
7. `recall_status`：召回状态，`0=正常, 1=召回中`。  
8. `remark`：备注。  

业务规则：

1. 删除批次前需检查是否存在生产记录、质检报告、溯源码、召回记录。  
2. 召回流程会同步更新该表的 `recall_status`。

#### 5.4.6 `production_record`（生产记录表）

用途：记录批次生产过程，形成时序化过程链。  

关键字段说明：

1. `batch_id`：所属批次ID。  
2. `record_type`：记录类型（如种植、施肥、用药、采收）。  
3. `operation_time`：操作时间。  
4. `operator_name`：操作人。  
5. `material_name/dosage`：投入品名称与用量。  
6. `content`：详细记录内容。  
7. `attachment_url`：附件访问路径（可为空）。  
8. `created_at`：创建时间。  

#### 5.4.7 `inspection_report`（质检报告表）

用途：记录批次的检测报告信息与结论。  

关键字段说明：

1. `batch_id`：所属批次ID。  
2. `report_no`：报告编号，唯一。  
3. `agency_name`：检测机构。  
4. `inspector_name`：检测人。  
5. `inspection_time`：检测时间。  
6. `result_status`：检测结果，`1=合格, 0=不合格`。  
7. `conclusion`：检测结论文本。  
8. `report_url`：报告文件地址（支持图片/PDF）。  
9. `created_at`：创建时间。  

#### 5.4.8 `trace_code`（溯源码表）

用途：建立批次与追溯码映射，是消费者查询入口索引。  

关键字段说明：

1. `trace_id`：外显追溯码，唯一。  
2. `batch_id`：所属批次ID。  
3. `qr_content`：二维码内容。  
4. `sign_value`：签名值（当前基于 `batchCode:traceId` 的 SHA-256 摘要）。  
5. `code_status`：溯源码状态，当前默认 `1`（可用）。  
6. `generated_at`：生成时间。  

#### 5.4.9 `recall_record`（召回记录表）

用途：记录批次召回事件的完整生命周期。  

关键字段说明：

1. `batch_id`：召回对应批次。  
2. `recall_level`：召回等级（1/2/3）。  
3. `reason`：召回原因。  
4. `recall_status`：召回状态，`1=进行中, 0=已关闭`。  
5. `notice_time`：通知时间。  
6. `closed_at`：关闭时间。  
7. `created_at`：创建时间。  

#### 5.4.10 `user_feedback`（用户反馈表）

用途：保存小程序端反馈，支持问题追踪与回访。  

关键字段说明：

1. `user_id`：反馈用户ID（登录场景下写入）。  
2. `type`：反馈类型（功能建议/体验问题/错误反馈等）。  
3. `content`：反馈内容。  
4. `contact`：联系方式（可选）。  
5. `trace_id`：可选关联追溯码，便于定位问题批次。  
6. `status`：处理状态，默认 `0`（待处理，可扩展处理流转）。  
7. `created_at`：创建时间。  

#### 5.4.11 表间约束与一致性策略

1. 强唯一字段用于业务去重：`username`、`base_code`、`batch_code`、`report_no`、`trace_id`。  
2. 高并发查询字段建立索引，保障分页与筛选性能。  
3. 服务层在删除与状态变更时做前置校验，避免“孤儿数据”或状态不一致。  
4. 通过 `created_at/updated_at` 支撑追踪审计与后续统计分析。

## 第6章 详细设计与实现

### 6.1 后端基础能力

1. 统一返回体：`ApiResponse<T>`（`code/message/data`）。  
2. 统一异常处理：业务异常、参数异常、上传异常。  
3. 鉴权拦截器：对 `/api/**` 进行 Bearer Token 校验。  
4. CORS：允许本地开发域名联调。  
5. 静态资源：上传文件映射为 `/uploads/**` 访问。

### 6.2 认证与账户能力

已实现接口：

1. `POST /api/auth/login` 账号密码登录。  
2. `POST /api/auth/wechat-login` 微信登录（当前实现为开发期模拟 openid）。  
3. `POST /api/auth/register` 用户注册。  
4. `POST /api/auth/bind` 绑定账号。  
5. `POST /api/auth/bootstrap` 初始化管理员。  
6. `GET /api/auth/me` 获取当前用户。  
7. `PUT /api/auth/profile` 修改当前用户资料（姓名、手机号）。

### 6.3 业务管理接口

1. 基地：`/api/bases`、`/api/bases/page`、`/api/bases/{id}`。  
2. 批次：`/api/batches`、`/api/batches/page`、`/api/batches/{id}`。  
3. 生产记录：`/api/production-records`、`/api/production-records/page`、`/api/production-records/{id}`。  
4. 质检报告：`/api/inspection-reports`、`/api/inspection-reports/page`、`/api/inspection-reports/{id}`。  
5. 召回：`/api/recalls`、`/api/recalls/page`、`/api/recalls/{id}`、`/api/recalls/{id}/close`。  
6. 溯源码管理：`GET /api/trace-codes`、`POST /api/trace-codes/generate`。  
7. 仪表盘：`GET /api/dashboard/stats`。  
8. 文件上传：`POST /api/files/upload`。

### 6.4 公开查询与反馈接口

1. 公开追溯查询：`GET /api/trace/{traceId}`。  
2. 反馈提交：`POST /api/feedback`。  
3. 我的反馈：`GET /api/feedback/my`。  
4. 健康检查：`GET /api/health`、`GET /api/db/ping`。

### 6.5 溯源码生成策略

1. `trace_id` 使用 UUID 去除连字符生成。  
2. `qr_content` 记录查询路径。  
3. `sign_value` 对 `batchCode:traceId` 做 SHA-256 摘要，作为后续防伪校验扩展字段。

### 6.6 管理端前端实现要点

1. 路由守卫校验登录态，未登录跳转登录页。  
2. `adminOnly` 路由限制用户管理页仅管理员可见。  
3. Axios 拦截器统一附带 Token、统一处理业务码与 401。  
4. 个人信息页改为“查看 + 弹窗编辑”交互，不在页面直接暴露编辑区。  
5. 仪表盘重构为 KPI + 业务对比 + 风险分析布局。

### 6.7 小程序端实现要点

1. 首页支持输入追溯码与扫码查询。  
2. 详情页展示聚合数据，支持检验报告预览页面。  
3. 查询历史按用户分桶存储，并支持回退读取历史兼容。  
4. 近 7 天查询量可视化采用稳定条形进度展示。  
5. 反馈页支持登录后提交与列表查看。

### 6.8 权限控制落地

1. 后端 `AuthPermissionService` 提供 `requireAdmin` / `requireStaff`。  
2. 业务管理接口统一执行 `requireStaff`（ADMIN/OPERATOR）。  
3. 用户角色接口执行 `requireAdmin`。  
4. 公共追溯查询接口不需要登录，确保消费者可直接查询。

## 第7章 系统测试与验证

### 7.1 测试目标

验证“功能正确性 + 权限边界 + 关键链路可用性”。

### 7.2 关键测试项

1. 认证测试：登录、注册、绑定、获取当前用户、修改个人资料。  
2. 权限测试：USER 调用管理接口应返回 403；ADMIN/OPERATOR 正常。  
3. 业务测试：基地/批次/生产/质检/召回 CRUD 正常。  
4. 溯源测试：生成溯源码后可公开查询聚合详情。  
5. 上传测试：图片/PDF 上传成功并可访问；超 20MB 返回明确错误。  
6. 小程序测试：扫码/输入查询、历史统计、反馈提交、报告预览。

### 7.3 测试结论

系统当前版本已具备毕业设计演示与功能验收条件，能够完成从管理维护到消费者查询的完整业务闭环。权限隔离、上传限制、异常处理和多端联调已具备可用性。后续可继续增强防伪校验、日志审计、自动化测试与部署编排。

## 第8章 软件使用说明

### 8.1 管理端使用流程

1. 首次部署调用 `/api/auth/bootstrap` 初始化管理员。  
2. 使用管理员/业务员账号登录管理端。  
3. 维护基础数据：基地、批次、生产记录、质检报告。  
4. 生成批次溯源码并导出/展示二维码。  
5. 风险场景下发起召回并在后续关闭。  
6. 在“个人信息”页通过弹窗修改姓名和手机号。

### 8.2 小程序使用流程

1. 首页输入追溯码或扫码。  
2. 查看基地、批次、生产、质检、召回详情。  
3. 通过历史页查看近 7 天查询量与历史记录。  
4. 在“我的”中完成登录/绑定并提交反馈。  
5. 在报告预览页查看图片/PDF 报告内容。
